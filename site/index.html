Breakpoint debugging for T-SQL, in VS Code.

Set breakpoints in a .sql file, press F5, and step through the statements while you watch the variables change. No Visual Studio, no SSDT.

What you get

The things a debugger has to do, done against a real SQL Server rather than a simulation of one.

Breakpoints that behave

Conditional breakpoints, hit counts and logpoints. A breakpoint inside a multi-line statement hits that statement; one on a blank line snaps down to the next.

Locals worth reading

Scalars, table variables and temp tables as expandable trees. Hover a variable to see it, put it in Watch, or change its value while paused.

Pause before, not after

The highlighted statement is the one about to run, and Locals shows the state before it runs. The same convention every other debugger uses.

Module mode

Press F5 on a CREATE PROCEDURE file and debug the body with a parameter form. Return values and OUTPUT parameters are reported at the end.

Dry runs

Wrap the whole session in a transaction and roll it back when you are done, so you can debug against real data without changing it.

Errors that point somewhere

A SQL error stops on the failing line with Locals intact. Parse errors go to the Problems panel instead of a dialog.

How it works

There is no secret debugging API in SQL Server. The trick is that your script is rewritten before it runs.

1
Your script is parsed and instrumented

Microsoft's own T-SQL parser finds the statement boundaries, and a call to a small pause procedure is spliced in between them.

2
The batch blocks at a breakpoint

The pause procedure waits inside SQL Server on the connection running your batch, which is what makes the stop real rather than simulated.

3
A second connection watches and reports

It notices the pause, captures the variables in scope, and tells VS Code. Stepping is a signal back the other way.

4
Nothing is left behind

The bookkeeping lives in a __dbg schema, which can be pointed at another database if you have no rights to create objects in the one you are debugging.

What it will not do

Worth knowing before you install it, rather than after.

  • It rewrites what runs. The instrumented script is not byte-for-byte the script you wrote. Statements are unchanged; pause calls are added between them.
  • A pause holds locks. A statement stopped mid-batch keeps whatever it has taken. That matters on a shared server, and it is why attach mode has a hard limit on how long it will hold a caller.
  • Scalar functions can never be paused. A UDF is not allowed side effects, so it cannot call anything that waits.
  • sqlcmd mode is not supported — no :r, :setvar or GO n.
  • Row counts are not shown. The instrumentation does its own inserts, which pollutes them, and a wrong count is worse than none.
